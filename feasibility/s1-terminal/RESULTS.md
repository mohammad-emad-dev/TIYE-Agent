Exit code 0 alone is not cited as proof; only the 9e re-enumeration is, and 9e itself terminates nothing. Non-Windows skips 9e without claiming a pass.

A keep-running PTY is intentionally owned, not an orphan. Output produced without a renderer is buffered up to one million characters; full pre-close terminal history is not replayed.

# Isolated Windows Job Object API probe — 10 October 2026 (isolated PASS, no 9f pass)

**Scope:** Standalone `CreateJobObject` / `SetInformationJobObject` (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) / `AssignProcessToJobObject` / `GetProcessTimes` / `IsProcessInJob` sequence via built-in Windows PowerShell + C# P/Invoke (`scripts/job-probe-controller.ps1`), driven by `scripts/run-job-probe.js` (`rtk npm run smoke:job-probe`). No Electron, no PTY, no mock-cli parent: the fixture is `mock-cli/mock-child.js` spawned directly with stdin held open (its contract — `exit` line exits, stdin close ignored, 60 s self-expire — is unchanged and no fixture file was modified). No new npm dependencies. No `taskkill` / `Stop-Process` / PID-only termination at any point; the only `kill()` targets are runner-owned `ChildProcess` handles (the controller, or the helper's own short-lived CIM enumeration on timeout) — never a captured fixture PID. Exit contract: 0 = job closure ended the exact child identity well before 60 s; 1 = READY but the child survived (normal stdin `exit` then observed); 2 = inconclusive/harness failure (never a pass).

| Check | Result | Evidence |
|---|---|---|
| No-job control | Pass | The mock child remained alive after about 2 seconds with stdin held open, then exited on an explicit stdin `exit` request (code 0). |
| Job setup and identity | Pass | `GetProcessTimes` checked creation time through the same opened handle used for assignment; CIM/FileTime skew was 3 ticks (300 ns), within the one-microsecond bound. The unnamed job's `KILL_ON_JOB_CLOSE` flag read back as `0x2000`; assignment succeeded and `IsProcessInJob=true` before READY. |
| Job-handle closure | Pass (isolated, exit 0) | The runner terminated only its controller `ChildProcess` handle. Read-only re-enumeration found the exact assigned child identity gone on the first attempt, 2,803 ms after child spawn, well before the 60-second self-expiry. The runner had held the child's stdin open, so the child did not exit on a pipe closure. |
| Earlier failed probe | Corrected implementation fault | Initial runs left the child alive because PowerShell changed a copy of the nested C# limit struct; the `KILL_ON_JOB_CLOSE` flag was never applied. The controller now assigns the modified struct back and queries the actual flag before READY. The earlier result does not establish a nested-job limitation. |
| Existing checks | Pass | `rtk npm run check` and `rtk npm run smoke:crash-baseline` pass; no Electron crash-baseline files or fixture behavior were changed by the isolated job probe. |

**What the job probe proves:** on this host, an unnamed job with the queried `KILL_ON_JOB_CLOSE` flag terminated one assigned mock child when the controller's last handle closed. The no-job control stayed alive. The controller checks PID plus creation time through the opened process handle with a one-microsecond conversion bound. This host appears to run these processes inside an outer job, so the successful assignment was nested.

**Limitations:** The probe used one child outside Electron and a PTY. It does not establish assignment of a main-owned PTY tree, inheritance by descendants, crash relaunch behavior with the job, verified-identity survivor cleanup, or vendor CLI behavior. S1 and 9f remain **partial**.

**Versions tested:** Windows 11 build 26300, Node.js 26.7.0, Windows PowerShell 5.1 + .NET C# P/Invoke (kernel32 only), TypeScript 5.9.3 (unchanged).
