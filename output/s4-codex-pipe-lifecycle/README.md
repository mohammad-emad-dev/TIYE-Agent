# Native pipe lifetime and blocked-writer capture

Recorded 16 October 2026. **Three synthetic peer scenarios and six capture tests
passed. S4/S6 remain partial; Phase 1 construction remains HOLD.**

This separate native Windows cohort follows the [first subprocess capture](../s4-codex-stdio/README.md).
It uses the [frozen framing policy](../s4-codex-framing/README.md) without changing
earlier measured source or evidence. No provider CLI, WSL, authentication, model
request, external command or descendant is launched by its fixed Python peers.
Host model reviews are separate activities in [review.json](review.json).

## What the capture establishes

| Scenario | Observation |
| --- | --- |
| `eof-pending-live` | Pending approval, then actual stdout EOF; local reply refusal; peer acknowledges a subsequent control probe on stderr; deadline terminates direct child |
| `eof-completed-live` | Completion record, then stdout EOF; peer acknowledges the subsequent probe; protocol completion does not clear the live-child deadline |
| `blocked-writer` | Peer leaves stdin open and unread; one 1 MiB write remains in `drain()` while both output readers continue; deadline cancels the writer with uncertain delivery and no retry |

The EOF peers read the fixed probe only after closing stdout. The parent sends
it only after observing EOF and closing the local approval path. The exact
standalone stderr acknowledgement is therefore evidence of peer execution after
the parent's EOF observation. This conclusion does not depend solely on a cached
`returncode` or a heartbeat already buffered before EOF. Both the EOF and
acknowledgement observations record a still-unset direct-child return code.

The post-EOF probe is **test control input**, not an approval response or a
product behavior recommendation. The pending approval is refused before that
probe is written; no denial or acceptance callback is transmitted in this cohort.
A locally drained probe alone is not acknowledgement; the exact peer message is
required by the capture test.

For the blocked writer, the parent records positive queued bytes via
`proc.stdin.transport.get_write_buffer_size()`, `drain-pending` state and an
unfinished writer task during repeated stdout and stderr reads. The capture
requires at least two such observations per channel and increasing observed
byte counts. The transport low/high water marks are explicitly 8,192/16,384
bytes. The 1,048,576-byte input is fixed fault-injection data and is never
evaluated by the peer. Its eventual delivered byte count remains unknown.

The writer is a separate task from both readers and the direct-child wait. A
blocked write therefore does not suspend stdout handling in this fixture. Its
deadline cancellation records `uncertain-write-cancelled`; there is one write
attempt, no retry, no `drain-returned` event and no peer acceptance claim.

All three scenarios intentionally end in `needs-attention`. Each records a
deadline fault, direct-child termination request, nonzero return code, completed
direct-child wait, settled I/O tasks and no cleanup errors. A protocol-completed
snapshot remains distinct from harness outcome; every `taskSuccess` is null.

## Scope and bounds

- Fixed absolute peer path, allowlisted scenario and Python `-I` mode; no shell.
- Activity deadline: 1.5 seconds **after subprocess creation returns**. Creation
  is not timed. This deadline also bounds the control-probe write.
- Independent stdout reads of at most seven bytes and stderr reads of at most
  4,096 bytes. Retained prefixes are capped at stdout 8,192/stderr 4,096 bytes.
  These are capture limits, not all Python/OS buffer-memory limits.
- Separate two-second direct-child wait and one-second stdin-close timeout.
  A timed-out stdin close aborts that transport and records a gate-failing error.
- Actual stdout EOF is recorded separately from a local policy disconnect on
  abort. In the blocked case, stdout EOF is not observed before cancellation.
- Captured bytes are the reads completed before cancellation. They are not the
  full output generated by the peer or a complete post-kill drain. A prefix may
  end mid-record; blocked-case tests validate it against the known emitted stream
  and parse only LF-complete records.

The peers have a roughly ten-second normal waiting/output path. The accepted
capture relies on deadline cleanup before that path ends. Native Windows
termination is tested here; Linux signal semantics, process trees, PID reuse,
Job Objects, crash recovery, persistent queues, arbitrary CLI behavior and
real-provider backpressure are not qualified. Private policy objects are a
convention, not a sandbox. No new approval authority is established.

## Evidence and reproduction

Sources: [harness.py](../../feasibility/s6-wsl/codex-pipe-lifecycle/harness.py),
[synthetic_peer.py](../../feasibility/s6-wsl/codex-pipe-lifecycle/synthetic_peer.py),
[test_capture.py](../../feasibility/s6-wsl/codex-pipe-lifecycle/test_capture.py),
[run.py](../../feasibility/s6-wsl/codex-pipe-lifecycle/run.py).
The [evidence index](evidence.json) pins source, frozen dependencies, schema
archive and probe/payload hashes, plus each scenario report, raw prefixes and
original test streams. Each scenario uses `.json`, `.stdout.bin` and `.stderr.bin`
files: [pending EOF](eof-pending-live.json), [completed EOF](eof-completed-live.json),
[blocked writer](blocked-writer.json).

From the repository root, with the recorded Python runtime and RTK installed:

```powershell
rtk proxy python -B -X utf8 feasibility/s6-wsl/codex-pipe-lifecycle/run.py --check
rtk proxy python -B -X utf8 feasibility/s6-wsl/codex-stdio/run.py --check
```

`--check` verifies hashes and six behavior assertions against saved captures in
the current process. It starts no new subprocess and makes no new timing claim.
The recorder without `--check` exclusively creates its output directory and
refuses an existing directory. One exploratory cohort and one preflight cohort
preceded the final sealed capture; their files were not substituted for it.
