**Draft acceptance outline only. Execution is not authorized by this document.**
It does not supply provider permission, select a different billing route or clear
Phase 1. Resolve the [route requirement](readiness.json) before authenticated
execution. The [existing inquiry draft](../s4-codex-candidate/PROVIDER-CLARIFICATION.md)

## Proposed staged observations

1. Verify executable/version and selected route conditions without inference.
   Stop on mismatch; preserve diagnostics, including helper startup warnings.
2. Establish the chosen native session/handshake and official authentication.
   Record only sanitized outcomes. Do not adopt the captured internal-use token
   login variant, transfer tokens from another CLI, or silently switch to API billing.
3. Run one bounded harmless task in the disposable worktree. Correlate owned
   request/thread/turn or the selected control surface's actual task identity.
   Verify the intended file/diff independently; protocol “completed” or exit 0
   alone does not prove the task outcome.
4. Qualify native approval callbacks in separately scoped cases. First observe
   deny/cancel paths with no allowed external effect. Any later permitted effect
   must have explicit operation/target authorization; no automatic session,
   execpolicy or network grant. Record resolutions and late-reply behavior.
5. Measure error/interruption/connection-loss cases separately from injected
   mock faults. A hung or uncertain task pauses for inspection; do not resend
   an instruction or reuse an approval. Resume/reattach requires its own native
   evidence and inspection of partial work before a replacement task.
6. Verify quit and abnormal-owner-exit cleanup in distinct cohorts. Do not infer
   Linux process-tree ownership from the Windows launcher or from the controlled
   detached mock recovery. A numeric PID alone is not a sufficient identity.
7. Extend to the remaining S6 filesystem, PTY, path, tool, environment and
   worktree rows only with the same qualified route/version and explicit scope.
   Preserve owner-side Git rules and prior failures.

Each stage can produce partial or failed evidence. A failed prerequisite stops
dependent stages; it must not be bypassed by retries, an unselected paid route or
rewriting the older capture. A new native cohort uses a new exclusive output
directory and a concrete reviewed protocol. Provider inquiry or registration is
not sent by this plan. The final product approval UI, durable core and team engine
are not required to perform these bounded feasibility observations.

## Exit criteria

Record pass/partial/fail **per supported claim**, update the version/environment
matrix and list remaining limitations. Separate provider scope, native access,
protocol completion, task outcome, ownership cleanup and production readiness.
Full S4/S6 and the Phase 1 gate remain open until their actual requirements are
closed or a separate explicit product/architecture scope decision is approved.
